# db

- `schema.sql` then `policies.sql` describe a fresh build; run them together as one transaction. A change to a table that already exists on the live project needs a file in `migrations/` with the same statements added to both files.
- `migrations/` holds the migrations: four per build slice and the server's functions. Apply them in this order, each once and as one transaction (the dashboard SQL editor, or `apply_migration` with the name in brackets); running one again does nothing.
  - `20261011000000_jio_invites.sql` (`jio_invites`), slice a: invite links and invitations by username.
  - `20261011000100_jio_meeting_spots.sql` (`jio_meeting_spots`), slice b: meeting spots, suggestions, "Works for me", `sessions.plan_version` and the two new meeting methods.
  - `20261011000200_jio_slot_details.sql` (`jio_slot_details`), slice c: `slots.details`. Folded into `20261022000000` (below), which starts with the same idempotent column add, so applying that one file covers stage 4; applying this one as well, before or after, is harmless.
  - `20261011000300_jio_session_plan.sql` (`jio_session_plan`), slice d: the suggested order, a stop's earliest start, Roam proposals and `session_travel_debt()`.
  - `20261013000000_jio_email_check.sql`: `email_registered()` is for the server only.
  - `20261020000000_jio_apply_session_plan.sql` (`jio_apply_session_plan`), stage 3: `apply_session_plan()`, the one function the server writes a session's plan through (the meeting spots). It needs slice b. The server's session endpoints call it, so apply it before deploying them.
  - `20261021000000_jio_drop_unreviewed_completion.sql`: drops two completion functions that were put on the live project by hand.
  - `20261022000000_jio_apply_session_plan_slots.sql` (`jio_apply_session_plan_slots`), stage 4: raises the length limit of a place's id from 80 to 160 on `slot_options`, `stops` (and `stop_proposals` when slice d is applied), so the 32 saved hawker centres (ids of 86 characters) can be options, and replaces `apply_session_plan()` so it also writes a voting session's slots and options as a difference, the votes that go with a member or a moved meeting area, the radius, and a banner stamped by the database. It also starts with `slots.details` (the column of 20261011000200, folded in with `add column if not exists`), drops every check on a place's id by what it checks (`pg_constraint`, whatever it is called) before making the checks of 160, refuses a part of a plan that the function does not know (`22023`), makes a swap of a place for itself a no-op, and writes a member's minutes only where they differ. It needs the stage 3 function (20261020000000). **Apply this one file, once, with the checksum guard, BEFORE the stage 4 backend runs anywhere (a laptop, a preview, the deployed server):** the backend sends slots, options and voting operations through the function, which the stage 3 function refuses or ignores, and stores place ids of up to 160 characters, which the old checks of 80 refuse. Slice d (`20261011000300`) is not needed by this stage.
  - `20261023000000_jio_apply_session_plan_stops.sql` (`jio_apply_session_plan_stops`), stage 5: folds slice d (`20261011000300`) in statement for statement (every statement is idempotent, so applying slice d as well, before or after, changes nothing) and replaces `apply_session_plan()` so it also writes the plan: the stops of a confirmed itinerary as a difference, a stop's new place with its details, the order note, the suggested order, the plan's start, Roam proposals, the moves `voting` to `confirmed`, `confirmed` to `voting` (opening the plan again) and `confirmed` to `completed`, and the travel ledger of a finished outing (its deltas must sum to zero). Every stage 3 and 4 rule is unchanged (`backend/tests/sessions-sql.test.js` compares the two functions line by line). It needs the stage 4 function (`20261022000000`). **Apply this one file, once, with the checksum guard, BEFORE the stage 5 backend runs anywhere:** the backend sends the stops, the ledger and the proposals through the function, which the stage 4 function refuses (`22023`), and reads columns and a table that exist only after it (or slice d). The order is therefore 20261022000000, then this file, then deploy the backend.
  - `20261024000000_jio_session_future_start.sql`: prevents direct client writes from creating a session on a past Singapore date or moving its start to an elapsed time today. Title-only edits to an old session remain allowed.
  - `20261028000000_jio_no_clashing_meetups.sql`: one person cannot be in two meetups at the same time. A meetup holds its time for the people joined in it (not opted out) while it is inviting, locating, voting or confirmed; completed and cancelled hold nothing, and back to back is allowed. What is refused, with `P0001` and the hint `schedule_clash` (the detail is the person's own meetup, as JSON): a person becoming joined in a meetup that overlaps another of theirs, by a link or an invitation (`join_session`), by the host's own row when a meetup is made, and by rejoining after opting out, whether the person writes it or the server does (`apply_session_plan`, op `rejoin`, which the trigger checks when the claim role is `service_role`); and a host moving a meetup's day or times onto a time the host is busy. A host moving it onto a time another joined member is busy is refused with the hint `member_clash` and no detail (it tells the host someone is busy then, not who or with what). The server's other writes, a new row inserted by the server, and the project's owner (no claims) are not checked. The trigger on `sessions` is `sessions_hold_time_clash`, named to run after `sessions_guard_future_start` so "That day has passed" (23514) wins over a clash; a host's move takes the advisory locks of the host and every joined member in sorted order. `apply_session_plan`, `guard_session_changes`, `sessions_guard_future_start` and `join_session` are not changed. Not applied to the live project yet: run `tests/no_clashing_meetups.sql` first, and the other tests with the migration installed.
  - `20261030000000_jio_outing_dietary.sql`: a member's dietary needs for one outing, and the host's dropped needs. Two server-only tables (`session_member_dietary`, one row per member who changed or confirmed their needs for the outing, removed with the member's row; `session_dietary_dropped`, the needs the host dropped, never tied to a person), with row-level security on, no policy and no privilege for `anon` or `authenticated`; and `session_member_needs()` (same signature and columns) answers each joined member's needs for the outing, their row if they have one, else their profile's. The host's drops are not taken off in the function: the server reads them from the second table. `apply_session_plan`, `guard_session_changes`, `join_session`, the clash functions and the account tables are not changed. Not applied to the live project yet: run `tests/outing_dietary.sql` first.
- `tests/` holds one access test per migration: `invites_access.sql`, `meeting_spots_access.sql`, `slot_details_access.sql`, `session_plan_access.sql`, `apply_session_plan.sql` (which tests all three of the function's migrations: steps 1 to 76 are stage 3's, 77 to 172 stage 4's (151 to 172 its smaller rules and the venue id checks), and 173 to 257 stage 5's: the confirm of the stops, stops as a difference, proposals, the ledger and finishing, the suggested order, and opening the plan again). Run each after its migration (and before the next slice) as one batch, as the project owner (`psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f db/tests/invites_access.sql`, or paste it into the SQL editor). A test needs the slices before it: b and d invite a person by username.
- Each test acts as each kind of user, ends with `rollback`, and so leaves no rows, passing or not. Each step prints `ok step N`; a broken rule stops the run with `FAIL step N`, and a run that passes prints `ALL STEPS PASSED`.
- `tests/session_future_start.sql` temporarily installs the future-start migration inside a transaction, checks signed-in direct writes, and rolls back the DDL and throwaway rows together. Run it as the project owner before applying the migration.
- `tests/no_clashing_meetups.sql` installs the clash migration (a copy, kept identical to the file) and the future-start rule inside a transaction, checks joining, rejoining (as the person and as the server) and moving a meetup, the statuses that hold time, opted-out members, and the order of the two `sessions` triggers, rolls everything back, and ends with a result row (`all 21 steps passed`). The meetups the other tests make for one person have different times, so every test passes with and without the clash rule.
- `tests/outing_dietary.sql` installs the outing-dietary migration (a copy, kept identical to the file; running it on a project that has it changes nothing) inside a transaction, checks that neither table is readable or writable by `anon`, a signed-in member (even on their own row) or the host, that the server reads and writes both, what `session_member_needs()` answers (the outing's needs over the profile's, the profile's otherwise, an opted-out member left out), the shape rules, the cascade when a member leaves or an outing goes, and the function's settings, rolls everything back, and ends with a result row (`all 32 steps passed`).
- Run a test on a new migration before applying it to the shared project; `seed/` holds the demo and venue data scripts and is unrelated.
