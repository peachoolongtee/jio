# Jio

Persistent project record for agents working in this repo. Keep it short: tasks and bugs live on the issue tracker, history lives in the work log, and this file holds what neither can tell you.

## Project Overview

Jio decides where a group should meet, fairly, and plans the outing around it. It is a graded IS216 group project by a six-person team. The repo owner is the team lead.

- **Shape:** a pnpm workspace with `frontend/` (Vue 3, Vite, Pinia, Leaflet on OneMap tiles) and `backend/` (Express on Node 24). The database is Supabase: Postgres, Auth and Realtime. Versions and scripts are in the `package.json` files; setup is in `README.md`.
- **Intended data flow:** the browser talks to Supabase directly for plain reads and writes, under row-level security. The backend exists for secrets and computation: the planner, OneMap routing and weather.
- **Three seams.** Change behaviour at these, and the rest of the code follows:
  - `frontend/src/lib/api.js`: every view and store reads and writes through its functions.
  - `backend/src/services/http.js`: every call to an external API goes through it, so stub mode can answer from fixtures.
  - `backend/src/db/supabase.js`: the server's token check, user-scoped client and service-key client.
- **Specification:** build spec v2 is kept outside the repo. `dev` has since grown a different product shape (sessions, not groups and events). Which one is the plan of record is an open decision on the tracker.

## Working Rules

- **`dev` is where work lands; `main` is held still.** Decided by the lead on 2026-10-11 for the pitch on 12 October. Nothing goes to `main` until the lead says. Work goes into `dev` through pull requests.
- **Commit and push only when the user asks.** When asked, make sequential commits with plain lowercase messages and no prefixes.
- **Code comments** are sentence case, and every function carries a "How to call" example.
- **pnpm only**, on Node 24.
- **Secrets:** report what kind of value a variable holds, never the value. Both `.env` files are git-ignored. `backend/.env` carries old database connection strings as comments; leave them for the lead to delete.
- **The live database is shared.** Before any schema change, list the project's migrations and tables. The account tables (`profiles`, `profile_private`, the sign-up trigger, `username_available`) were made by a teammate; build on them and leave them as they are.
- **Teammates' branches and pull requests are read-only.** Review them; change them only when the user says so.
- **Test database changes in a transaction that rolls back**, so no rows are left on the live project.

## Architecture Decisions

Each is recorded in full on the ticket named. Read the ticket before changing the behaviour.

- **Token check:** the backend verifies login tokens locally and loads data as the signed-in user, so the database's rules decide access. The service key is for server-owned writes only. Ticket #8.
- **Stubbing:** one HTTP helper answers from fixtures in stub mode; a request header picks the scenario. Ticket #9.
- **Constraints:** dietary needs filter food venues only; CDC and Culture Pass are ranking boosts. Ticket #35.
- **What the group sees of a member is their area, never the exact place.** Area ids are on `session_members`. Labels and coordinates are in `session_member_places`, which only the owner and the server read.
- **Private planner needs** (home area, dietary, budget, step-free) sit in `profile_private`. Only the owner and the server read them, through `session_member_needs()`. **No need is named in anything every member reads**: `slot_options.details` stores one flag, `checkNeeds`, never `verify` or `dietUnknown`, and the search of a slot's places says `group_needs`, never `diet:halal` or `step_free`, because in a group of two a named need is the other person's. The browser names the needs it may (its own, and the others' once `GET /api/sessions/:id/dietary` gives them at three joined) from each venue's own diet levels; otherwise a card says "Check it fits everyone's needs".
- **What a browser may write directly:** a new session; a host's title, date and times, start and cancel; a member's own start and end area and exact place while the session is open; a member's own "Works for me" while it is locating; a member's own picks (categories and how long they stay) and **votes** while it is voting (a trigger, `votes_guard_status`, refuses a vote once the session is no longer voting, and waits for a confirm in progress); a host's invite links; a host's start choice (`sessions.meet_by`, `'fairest'` or `'known'`) in the update that starts the session or while it is locating, never cleared. **Everything else goes through the server, all of it through the one function `apply_session_plan`:** the spots, suggestions, the host's confirm and known place (stage 3), opting out and rejoining, leaving and removing a guest while inviting or locating (a member's row is deleted only there, with the spots worked out again in the same write; voting and later are refused), and, since stage 4, the slots, their places, the radius, a swap and "more suggestions" (a vote is never written by the server: it only reads them, and takes a person's votes with them when they opt out, leave or move the meeting area). Since stage 5, the server also writes:
  - the plan's confirm, which is refused unless every stop is still the vote leader of its slot (`stale_tally`, answered as 409 `order_stale`) and the host's basis matches;
  - the stops and their edits, and re-plan;
  - finishing the outing and its ledger: the host only, on or after the outing's day, and nothing finishes a shared outing by a clock;
  - Roam proposals, and the host's kept rain warnings (`sessions.weather_kept`);
  - opting out of a confirmed plan, which raises `sessions.replan`. Leaving and removal stay refused once voting starts, by the lead's decision of 26 October;
  - **the host's change of the meeting place** (`POST /api/sessions/:id/change-meeting-place`, the op `release_meeting` of `apply_session_plan`, migration `20261027000000`, written and not yet applied): from voting or confirmed back to locating, in one write that lets the meeting area go and clears the votes, slots, stops, spots, approvals, suggestions and the plan's columns and records the host's new `meet_by`. Starts, ends, exact places and picks stay. "Known" is then a second write, the known place, with the notice brought along. The server tries a write once more after a deadlock (40P01 or 40001), the browser sends the `planVersion` it saw (409 `stale_plan`), and the migration must be applied before the backend that has the route runs.

  The server also records `meet_by = 'known'` after a known place is set. The function writes nothing if the session's version or status is not what the server loaded, raises the version only when something changed, and never moves a chosen meeting area, with one exception: the host's release (`release_meeting`, above), which is the only way a `voted` or `chosen` area is let go (every other path still answers `area_pinned`). A run that priced the spots again moves their `computed_at` forward without raising the version, which is how a page tells a start was never priced. `sessions.banner` is `null` or `{ text, at, approvalsRemoved: true }` (or `{ text, at, votesCleared: true, byRadius? }`), written only by that function (`backend/docs/planner-api.md`). The trigger `guard_session_changes` and the access rules enforce the rest.
- **Token check:** the server holds its own copy of Supabase's public signing keys and verifies only `ES256` and `RS256` tokens whose key id it holds. It answers 503 when it cannot reach Supabase and has no keys. After a failed refresh it waits a minute before asking again, and it drops keys older than 24 hours. `SUPABASE_ALLOW_LEGACY_TOKENS=1` admits `HS256` tokens by asking Supabase.
- **Errors:** only an error raised by the body parser may answer a 4xx by its own status. Any other uncaught error answers 500 and is logged, so an external API's 401 never reaches the browser as one.
- **`db/schema.sql` and `db/policies.sql` describe a fresh build** and run together as one transaction. A change to a table that already exists on the live project needs its own migration, with the same statements added to the files.
- **Weather:** the planner scores against the live two-hour forecast and says where the weather came from in `weather.source`. A simulated forecast needs `ALLOW_SIMULATED_WEATHER=1` or stub mode; otherwise `weatherCase` is ignored, never refused, because the frontend sends it on every ranking.
- **One error shape:** `{ error: '<code>', message }` on every route. Decided by the lead on 2026-10-09, replacing the nested shape on ticket #8.
- **Rate limit:** the planner routes share a per-caller limit set in `index.js`. `createApp` applies none unless given `planRateLimit`, so tests are unaffected.
- **Sample data: partly labelled, by the lead's decision of 2026-10-10.** The lead took the leaderboard pull request as shipped, which removed the "Sample" note from the leaderboard, Home's places and the Rewards banner. It remains on the place detail and on other people's profiles; rewards use invented café names; distance-based times say "about". Do not add or remove notes without the lead.
- **Cut on 2026-10-09:** crowd estimates, "Ask AI", and the contacts and location steps in sign-up. Do not bring them back without the lead.
- **Contrast: the brand red is `#ff385c`, by the lead's decision of 2026-10-10.** White text on it is 3.52:1, below the 4.5:1 minimum, and three category and three person colours are also under it. `DESIGN.md` lists each pair under "Known Conflicts". Do not darken them without the lead; do not add new white-on-red text without reading that section.
- **OneMap is a shared budget.** The account allows 300 calls a minute for everyone. One request routes at most 60 trips, whole candidates only; the whole server makes at most `ONEMAP_CALLS_PER_MINUTE` calls (240 by default) across routing, search and login; a trip over either limit falls back to the table of real times between the areas (`travelSource: 'table'`) and, where the table has no pair, to the straight line, flagged `approximate`. Do not add a OneMap call that bypasses `createOneMap`'s budget. **Rank on the table, route only what is shown** (table mode, `runWithTableTimes` in `services/travel-times.js`): every area and place is ranked on `area-times.json` with no call, and only the best 3 places and the best 2 meeting areas (the chosen first) are routed, then the engine runs again and a candidate that climbs into them is routed in the next round (`TABLE_ROUTE_ROUNDS`, 3, none after 500 ms or less is left); unrouted candidates are read on the table moved by how far that person's routes in this request differ from it (±15 minutes at most). The ranking reads a candidate live only if it showed it first in this request, cached or not; the areas a person names are routed last with the trips the ranking leaves, and a route bought for a name serves only that area's own entry, so a name cannot move the pick, the order or the routes the ranking buys. A candidate is read whole, routed or table, never half and half; a candidate that is never shown is never fetched. `travel` gains `table` and each result `travelSource` (`routed`, `table`, `estimate`); `approximate` stays about the straight line alone, and the screens and the stored session columns say "about" for `approximate` or `table`. Do not rank on live routes again. The routing deadline is 3 s by default (`ROUTING_DEADLINE_MS`) and starts when routing starts, not when the request does; sample-data builds (the showcase and the tour) send `travel: 'estimate'` and never route (with the table they use its times, free).
- **Google is a paid budget.** Every Google call goes through the budget in `createGooglePlaces`: `GOOGLE_CALLS_PER_MINUTE` (60 by default) for nearby searches and photos together, three failures pause it for a minute, and each call times out after 3 seconds. A call that queued for a slot for a second or more is refused (`waited_too_long`) when the last completed call failed, and a lane is not charged for a call refused before it made a request. Google failing never fails a planner request. Do not add a Google call that bypasses it, and never write Google content to a file: fixtures are invented. **Google tops up, it does not flood** (ticket #149, decided with the lead on 16 October 2026): it is asked only about categories where we know fewer than 6 open places near the meeting point (the answer's `google` block says `not_needed` with `reason: 'enough_own_places'` otherwise), food and drink need 20 Google reviews to be added, at most 2 of the first 5 places of a category are Google's, and a rating counts as far as its reviews (`weightedRating` in `scoring.js`; a place with no rating or no review count, which is every curated, OneMap and CDC place, counts as 4.0, while the invented mock venues, served only with `INCLUDE_FICTIONAL_VENUES=1`, carry review counts and are scored on their ratings). The count of our own places uses the engine's own hard filters (`hardFilterContext`), and the cap of 2 Google places is on the first 5 places whatever `topN` is. The rating weight scales with the weights a request sends, so its share stays the same.
- **Saved places are repaired and filtered in code, not by hand.** `onemap-places.json` is written only by `pnpm build:onemap-places` (network, needs the OneMap account) or `pnpm repair:onemap-places` (no network). Duplicates, places that are not somewhere to go, and closed weekdays are worked out at load in `backend/src/db/venues.js`.
- **A guessed price makes no claim for any place** (the lead's decision of 2026-10-11): a venue with `dataQuality.priceAssumed`, whether from OneMap, Google or CDC, gets no "Budget friendly" tag and no "within budget" sentence, through `priceIsKnown` in `backend/src/planner/scoring.js`. The price still counts in the score and in the `max_price_pp` filter. Only the curated and mock venues with hand-entered prices can carry the claim.
- **The AI is a paid budget too.** `POST /api/itinerary/arrange` asks an AI to choose among orders the rules allow. Every AI call goes through one budget (`ITINERARY_AI_CALLS_PER_MINUTE`, 20 by default, 2 at once), a 10-minute cache, a pause after three failures and an 8-second deadline; anything else answers by the rules. Only venue names, kinds, times and the weather go to the provider, never anything about a person.
- **Local accounts in a production build are off** when Supabase is set up, and a production build with no Supabase settings refuses to run. `VITE_ALLOW_LOCAL_ACCOUNTS=1` turns them on, which a deployed demo needs.
- **One way to change a confirmed stop's place.** `changeStopPlace` in `frontend/src/lib/api.js` is behind both the rain swap and Replace: the host only, refused when the stop no longer holds the place the caller saw, and the stop never starts earlier than the time the planner checked it for. Do not add a second way.
- **Meeting spots:** a planner answer computed before the host confirmed is never applied afterwards, and a failed write takes back only its own change (`latestAnswer` and `orUndo` in `frontend/src/lib/api.js`). Naming an area in `include` never changes the planner's own pick.
- **Google places may not be shown on or beside the OneMap map** (Google's terms, read on 2026-10-11). "What next?" draws a OneMap map beside its list, so it leaves Google places out of both (`isGooglePlace` in `RoamPanel.vue`). Read the research on the map before building a screen that shows them.
- **Planner limits:** every list, string and number in a planner request has an upper bound, held in one `MAX` block in `backend/src/routes/plan-schemas.js`.
- **Routes added to the Express app go in through `createApp({ mount })`**, because the "not found" handler is last.
- **Dietary needs (ticket #107):** food places are filtered strictly for the group's needs (`dietPolicy` in `frontend/src/lib/api.js`, sent as the request's `dietPolicy`, which leaves `unknownPolicy` for `near_mrt`, `step_free` and `sockets` as it was); a drink stop is changed only by halal, which keeps bars out (`meetsDiet` in `backend/src/planner/filters.js`). The group's needs travel on the first member sent, so a need is never tied to a person, even in the request. Only the signed-in person's own need and the sample friends' (`SAMPLE_DIETARY`: Faith halal, Nicole vegetarian) are known until sessions are on the server (#80). Fewer than 3 food places that fit offers "Show places we couldn't confirm" (`session.unconfirmed`); those are ranked by how many of the group's needs they likely meet, most first, then by score (`byDietFit` in `backend/src/planner/engine.js`, also when the shortlist is cut). A need changed mid-vote re-ranks and shows a banner that names nobody. Caveats are tags on the card ("Halal likely", "Halal not confirmed" with a warning icon), halal brown and vegetarian and vegan green (`--diet-halal-*`, `--diet-veg-*`, both over 6:1). Each person is asked to "Confirm dietary needs" once per outing when it reaches voting (`DietaryConfirm`, `session.dietChecked`), with the others' needs selected and unnamed. A person's picks there, and on Vote's chips, are for that outing only (`session.dietMine`, read first by `dietaryOf(id, session)`); the profile is their standing setting and starts each outing. On the server it is `session_member_dietary` (below). With fewer than three people joined nobody else's needs are listed (`others` is empty on the server and in `othersNeeds`), so there is no "Unselect"; the places are still filtered for them. A need someone else has can be unselected, in an outing of three or more, after a second dialog ("Unselect halal?") reminds the person that someone in the outing needs it; the outing then stops filtering for it (`session.dietDropped`, `confirmDiet(id, mine, dropped)`), and selecting it again brings it back. "Group dietary needs" on Vote (the needs selected below, as tags), laid out like "Search within", holds the same Halal, Vegetarian and Vegan chips (`DietaryChips`, with the same "Unselect halal?" warning), saved at each tap. Any change to the group's dietary filter picks the places again (`syncOptions(session, { fresh: true })`): only voted places that still fit stay, the rest are the planner's best for the new needs. Sign-up has no dietary question (the ticket's "Not in sign-up"): a popup asks once per account ("Any dietary needs?", `DietaryFirstAsk` in the app frame, opened by `auth.signUp`, and for a real account never asked, by `auth.init` and `auth.signIn`), and saves the answer on the profile. That it was asked is remembered in this browser (`jio-diet-asked:<account id>`), and a saved need counts as asked; a reload keeps the question until it is answered. The ticket's question at the first outing created or joined was tried and replaced by this at the user's word (21 October 2026). An account that must confirm its email first is asked at its first sign-in. For a session on the server, the needs come from `GET /api/sessions/:id/dietary` (needs together, no names, read with the service key through `session_member_needs()`; `outingDietary` in `api.js`). It is unused on screen until voting moves to the server, because a shared session cannot open Vote yet.
